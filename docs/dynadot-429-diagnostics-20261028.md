# Safe Dynadot 429 diagnostics and verified route recovery

The preceding release removed avoidable cross-account bursts, but scheduled reads still received HTTP 429. On 28 October a controlled comparison used the same founder account and account-info endpoint: its managed route returned 429, the existing residential proxy succeeded, then the managed route again returned 429 after cooldown. One inventory GET per affected founder account through that existing proxy succeeded with complete inventories matching the stored account counts. No credentials were changed or copied to new local secret files; credential material was used in memory. Application caches were not updated by these diagnostic reads.

This establishes a route-dependent failure and a working existing route. The comparison also changes client transport, so it does not by itself prove an IP ban or identify Dynadot's internal quota key. The repair uses a guarded encrypted default proxy profile visible in Settings, referenced only by the four verified founder Dynadot accounts; other customers and registrar routes retain their existing settings. A separately qualified alternate route uses its own durable serial queue with the existing conservative close cooldown, so concurrent account syncs cannot recreate the original burst or share the failing managed IP's cooldown. Changes must wait for the concurrent engine-19 production writer to finish and use guarded atomic encrypted routing updates, with protected-data comparisons and fresh real application sync acceptance afterward.

The software retains only allowlisted 429 facts: concurrency/request-rate/daily-quota/edge-challenge/unknown category, endpoint family, response format, positive retry timing/source and validated correlation IDs. Raw response bodies, URLs, query strings, credential values and domain names are excluded. Existing rate-limit error classes and shared/local cooldown markers survive. Old diagnostic records remain readable; the quiet mail policy and ordinary schedules are unchanged.

A real-SDK fault test failed before the transport change because arbitrary error body text survived and safe classification was missing. It passes with the normalized response. Storage/schema tests prove that safe details survive recording, and old records do not require migration. The encrypted routing patch is independently tested for all-or-nothing compare-and-swap behavior and preservation of unrelated accounts.

After release, qualification requires the exact engine/source, preserved identities/keys/eligibility/pauses, successful real inventory syncs for all four accounts with last-good timestamps advanced and prior failures cleared, accurate pricing status, and fresh monitor observations. Diagnostic comparison success alone does not establish application-cache recovery. No registrar purchase, renewal, transfer, deletion or domain-settings mutation is permitted as a test.
