# Hosted checkout reservations

The reservation store uses the control database to enforce one active hold per canonical domain across hosted workspaces. An approval binds the case, seller, listing, publication revision and directory generation, exact amount and currency, provider, and expiry. Replaying an approval returns the same reservation. Changing the submitted terms requires another approval. A fresh approval can reclaim an expired hold that never entered provider creation.

The store persists the creation intent before the provider call and gives retries one stable key. A timed-out or withdrawn quote with a creation intent stays held while the provider session is reconciled. When a creation response arrives after withdrawal, the stored session is available for cancellation. The buyer must receive a checkout link only while the current reservation and publication are eligible.

A provider adapter must authenticate notifications, retrieve the canonical session using the merchant reference, and pass observations with stable event IDs and exact normalized amounts. The observations journal rejects conflicting reuses and records payment and authoritative transfer evidence independently. The reservation advances to transferred after both facts are present. A final cancellation may release an unpaid session only when the provider establishes that the session can no longer accept payment. A refund must establish that funds were reversed and the transfer can no longer complete. Contradictory evidence following a provider's purported finality holds the canonical domain for operator review. While that hold is present, the coordinator cannot create a new session or return an existing checkout link. Any replacement session whose creation was requested is marked for cancellation and still needs authoritative provider reconciliation. A completed transfer blocks resale until the new ownership and publication are reviewed.

The rollout requires a seller-approved provider sandbox, a live check of the verified case and exact current quote, and enforceable publication and external-channel interlocks. The directory is a locator. Tenant withdrawal or a registrar or marketplace change can occur independently of it. Qualify the pending-session cancellation and transfer-evidence contracts with the selected provider before exposing any buyer checkout links.

## Isolated staging qualification

The simulator is available only on an isolated `domains-*-qa-<8 hex>.<account>.workers.dev` canonical origin with public registration disabled. Deploy `src/hosted/checkout-simulator-worker.ts` as a private Worker with a SQLite `CheckoutSimulatorLedger` Durable Object, no public routes, and a dedicated `CHECKOUT_SIMULATOR_KEY`. Bind it to the staging gateway as `CHECKOUT_SIMULATOR`. Set the same key on the gateway and set `CHECKOUT_STAGING_WORKSPACE` to the controlled seller account. Apply control migration 0028 and deploy the compatible tenant wrapper to that account first.

The seller opens `/checkout/staging/approve` and reviews the current published quote for a verified Sales Inbox case. Approval reserves that exact domain, case, price, currency, and listing revision for 15 minutes. Use a disposable listing without another provider destination. The verified buyer opens staging checkout from the existing private conversation. The simulated session stays in staging and accepts no payment or transfer instructions.

The simulator journals one session per reservation and can drop the first creation response after persisting it. Its private qualification routes let a test inject observations and send the returned signed callback body and signature in any order. The gateway checks the signature and reads the canonical simulator session before recording evidence. Keep simulator controls on the private binding. Remove the fixture session and reservation through the isolated test cleanup and verify both counts are zero.

Run `npx vitest run src/hosted/checkout-reservations.test.ts src/hosted/checkout-flow.test.ts` to exercise the reservation state transitions and the authenticated case-to-simulator path. This suite uses local D1 and Durable Objects. A seller-approved escrow sandbox, authoritative cancellation and transfer evidence, and exclusivity across active sales channels are separate launch requirements.
